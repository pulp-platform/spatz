# 4. Spatz VME Microarchitecture

## 4.1 Implementation Overview

The Spatz VME implementation extends the vector execution subsystem with matrix configuration state and an Outer Product Engine (OPE) that contains a distributed accumulator array and a distributed FPU array. The architectural behavior of the Zvt instructions and matrix tile state is defined in the preceding chapter. This chapter focuses on their hardware implementation and integration with the existing Spatz vector datapath.

The decoder classifies Zvt instructions according to the instruction categories defined by the specification. Matrix Configuration Instructions, including `msetmtype`, `msetmtypei`, `msettn`, `msettm`, and `msettk`, are executed by the Spatz controller. Matrix Arithmetic Instructions, including `vtfmm`, `vtfmm.alt`, `vtmmu`, and `vtmms`, are dispatched to the OPE. Move Tile Subset instructions (`vtmv.v.t` and `vtmv.t.v`), the Matrix Tile-Zero instruction (`vtzero`), and the Zvt Context Discard instruction (`vtdiscard`) are also handled by the OPE. Load/Store Tile Subset instructions (`vtle` and `vtse`) are dispatched to the VLSU.

The VAU, OPE, and VLSU have distinct execution roles. The VAU executes conventional RVV arithmetic operations. The OPE performs matrix arithmetic, maintains the accumulator tile state, and moves tile subsets between the distributed accumulator array and the VRF. The VLSU performs vector-memory transfers and moves tile subsets directly between memory and the distributed accumulator array through the Tile interface.

The controller assigns every issued RVV or Zvt operation an instruction identifier from a common pool of eight identifiers. The identifier remains associated with the operation while it is buffered or executing and is returned by the execution unit with the completion response. The controller uses it to associate an operation with its vector-register dependencies, accumulator-tile dependencies, execution-enable signal, and retirement state. RVV and Zvt instructions can therefore share one dependency domain while executing in the VAU, OPE, or VLSU.

Request acceptance and execution eligibility are decoupled. An OPE or VLSU queue may accept a request before its recorded dependencies have been resolved. The controller later enables that request through its instruction identifier, and the execution unit combines this enable with its local resource availability before executing the operation. This separation between queue admission and execution eligibility allows the execution units to absorb temporary VRF, arithmetic-pipeline, accumulator, and memory backpressure.

The distributed accumulator array has three hardware access paths. The FPU array uses its internal read and writeback paths for matrix arithmetic. Tile subset moves use the OPE's VRF-facing path. Tile subset loads and stores use the Tile interface between the VLSU and the accumulator array, without transferring their data through the VRF.

## 4.2 Shared VRF Access and VAU–OPE Arbitration

The OPE reuses the existing Spatz VRF for matrix operands and tile subset moves. The VRF provides three 256-bit read ports and one 256-bit write port. The Spatz top module adds three fine-grained round-robin arbitration points that select between VAU and OPE requests when both units request the same port resources in the same cycle.

The first arbitration point controls the first two VRF read ports as one atomic operand pair. A VAU instruction uses the pair for its vector source operands, while an OPE Matrix Arithmetic Instruction uses it for the left-hand and right-hand matrix operands. The selected requester receives both ports together, preventing the two operands of one operation from being split across different execution units.

The second arbitration point independently controls the third VRF read port. The VAU uses this port for operations that require a destination-vector read. The OPE uses it for `vtmv.t.v`, which reads a vector-register group and writes the data into a tile subset of the accumulator array.

The third arbitration point controls the VRF write port. The VAU uses this port for conventional vector-result writeback, while the OPE uses it for `vtmv.v.t`, which writes an accumulator tile subset into a vector-register group. Each arbiter returns a grant only to the selected requester, so a losing request remains asserted and is backpressured until the required port becomes available.

The VLSU retains separate VRF-side interfaces for conventional vector loads and stores. Load/Store Tile Subset instructions use the independent VLSU–accumulator Tile path and do not request the shared OPE/VAU VRF ports.

Sharing the existing ports avoids increasing the VRF port count and the associated storage and interconnect cost. The trade-off is increased contention when VAU pre-processing or post-processing overlaps OPE execution. Simultaneous requests cause one unit to wait for the round-robin grant, which can delay operand delivery or result writeback and reduce the amount of useful overlap between vector and matrix execution. The impact therefore depends on the scheduling of vector preparation, matrix arithmetic, and vector post-processing around the shared-port demand.

## 4.3 Controller and Dependency Management

The Spatz controller coordinates architectural state and dependencies across the vector and matrix execution units. It maintains the matrix configuration, allocates the common instruction identifiers described in Section 4.1, and records vector-register and accumulator-tile dependencies for in-flight operations. The resulting per-identifier dependency state controls when a queued operation may begin execution.

### 4.3.1 Matrix Configuration State

Matrix Configuration Instructions are executed by the controller. The controller maintains `mtype` together with the existing RVV configuration state and derives the active SEW, TEW, TWIDEN, LMUL, `vl`/`tn`, `tm`, and `tk` values used by subsequent Zvt operations. It applies the limits defined by the Zvt configuration rules and by the implemented tile edge, vector length, element widths, and maximum reduction extent.

The controller also implements the Zvt requirement that every Vector Configuration Instruction invalidates the current matrix type state by clearing `mtype`. Conversely, `msetmtype` and `msetmtypei` update both the matrix and vector configuration fields required for matrix execution.

Each dispatched Zvt request carries a snapshot of the relevant vector and matrix configuration. A request already buffered in the OPE or VLSU therefore retains the interpretation established when it was dispatched, even if a later configuration instruction changes the controller's architectural state.

### 4.3.2 Vector Register Scoreboard

The controller maintains VRF read and write tables indexed by physical vector register. When an instruction is dispatched, these tables are used to construct RAW, WAR, and WAW dependencies between its instruction identifier and older in-flight operations.

For a vector register group, the scoreboard records every physical vector register selected by LMUL rather than recording only the aligned base register. This preserves dependencies across changes between vector configurations established by `vsetvl` and matrix configurations established by `msetmtype`, even when the two configurations interpret the same architectural register specifier with different group sizes.

For Matrix Arithmetic Instructions, the scoreboard records both explicitly encoded source register groups and the implicit row-stride groups required by Zvt when `tk` is greater than one. Successive operand rows are separated by `8/KMAX` vector registers, and every LMUL-sized register group belonging to each active row is entered into the read table. A later writer therefore remains ordered after every explicit and implicit source group of the matrix operation.

### 4.3.3 Matrix Tile Scoreboard

The controller maintains a separate matrix scoreboard for accesses to accumulator tiles. Each dispatched tile operation creates a claim containing an accumulator-tile mask, read and write attributes, its execution-unit class, and dependencies on older overlapping claims. The mask accounts for the aliasing of logical tile identifiers at different TEW values.

A dependency is recorded when the new claim overlaps an older accumulator-tile claim and at least one of the two accesses writes the selected state. The controller removes the dependency when the older OPE or VLSU operation returns its completion response. For each instruction identifier, `matrix_enable` is asserted only when its recorded matrix dependencies are empty.

Every queued OPE and tile-memory request is gated by its `matrix_enable` signal before it becomes eligible for execution. The exception in dependency construction is a Matrix Arithmetic Instruction following another Matrix Arithmetic Instruction: the controller does not create a MAC-to-MAC tile dependency because the OPE can preserve their program order and forward a pipeline-resident partial sum to a subsequent compatible update. Such a MAC still checks `matrix_enable`; it is simply not blocked by older MAC claims. It may remain blocked by an older overlapping move, load, store, zero, or discard claim.

After a MAC request passes the controller-provided enable, the OPE performs the physical hazard checks required by its implementation. It compares the requested tile and spatial beat with pipeline-resident result tags to decide whether the update can consume a forwarded addend, must wait for an earlier beat, or must switch the resident tile and write older results back. These OPE checks determine when the arithmetic request can execute and complement the architectural ordering enforced by the controller scoreboard.

### 4.4.1 Organization

The OPE contains a distributed accumulator array, a distributed FPU array, and control logic for request buffering, spatial scheduling, result forwarding, accumulator writeback, and tile subset moves. The two arrays are spatially aligned: every FPU lane is paired with one lane-local accumulator bank. In the current implementation, the compute edge is CE = 8, producing an 8 × 8 compute array with 64 FPU lanes and 64 accumulator banks.

The accumulator banks hold materialized tile state. The FPU pipeline can temporarily hold a newer version of the elements currently being updated. This distinction permits successive Matrix Arithmetic Instructions to forward partial sums through the FPU pipeline instead of writing and rereading the accumulator after every instruction.

### 4.4.2 Request Queues and Operation Selection

The OPE separates incoming requests into four operation classes. Matrix Arithmetic Instructions enter a four-entry, non-fall-through FIFO. Tile-to-vector moves, vector-to-tile moves, and tile-clean operations each use a dedicated spill-register queue.

A Matrix Arithmetic Instruction can occupy the OPE for more than ten cycles because its vector groups, reduction rows, and spatial beats are processed over multiple cycles. The four-entry MAC FIFO allows several later arithmetic instructions to wait close to the compute datapath. Buffered work can therefore remain available when Snitch stalls or does not immediately supply another MAC, reducing gaps between long-running Matrix Arithmetic Instructions and helping keep the FPU pipeline occupied.

The MAC FIFO is non-fall-through so a newly accepted request is registered before it is considered for execution. On the following cycle, the controller's registered dependency state and the request's `matrix_enable` value are available together. This avoids a combinational path in which a request could pass directly from dispatch into the MAC scheduler before its dependencies have been recorded.

The four queue heads are considered using a fixed priority: tile-clean, tile-to-vector, vector-to-tile, and finally MAC. A queue head participates only after its `matrix_enable` signal is asserted. The selected operation must also find the resource used by its class available: a move requires its move datapath and accumulator access to be idle, while a MAC requires space in the MAC scheduler and no conflicting tile-interface access or resident-tile drain.

If a queue head is not selected, its valid bit and request payload remain in that queue. It is reconsidered in a later cycle after the higher-priority operation advances or the blocking resource becomes available. Backpressure reaches the controller only when the corresponding queue can no longer accept another request.

### 4.4.3 Distributed Accumulator Array

The accumulator array stores tile state across CE² lane-local banks. Each bank uses 32-bit physical words, matching the default TEW = 32 accumulation configuration. When TEW is narrower, such as TEW = 16 or TEW = 8, a logical tile selects a half-word or byte slice of the same physical word. Byte-enable signals allow one slice to be updated while preserving the neighbouring logical tiles that share the word.

Zvt constrains the tile edge TE to a power of two. The implementation may choose a TE larger than the physical compute edge CE, in which case a logical TE × TE tile is divided into CE × CE spatial beats. The number of beats per physical tile slot is

```text
SpatialBeats = (TE / CE)².
```

Each bank contains four TEW = 32 physical tile slots, so its accumulator depth is

```text
AccDepth = 4 × SpatialBeats.
```

For TE = 16 and CE = 8, one tile contains four spatial beats and every bank contains sixteen 32-bit words. The complete distributed accumulator has a capacity of 64 × 16 × 32 bits, or 4 KiB.

For an element at logical coordinates `(row, col)`, `row mod CE` and `col mod CE` select the lane-local accumulator bank. The upper coordinate bits select the spatial beat:

```text
beat_row    = floor(row / CE)
beat_column = floor(col / CE)
spatial_beat = beat_row × (TE / CE) + beat_column.
```

The logical tile identifier selects the physical tile slot and the active byte range within its 32-bit word. The physical address within a lane-local bank combines the physical tile slot with the spatial-beat index.

### 4.4.4 Distributed FPU Array

The CE × CE FPU array performs one outer-product update for the spatial region selected by the scheduler. A CE-element segment from the left operand is distributed across the compute rows, and a CE-element segment from the right operand is distributed across the compute columns. The FPU lane at `(r, c)` updates the accumulator element associated with that compute-array position.

The FP32 path uses one FMA datapath per lane. The widening FP16-to-FP32 path uses an SDOTP datapath that multiplies two pairs of FP16 subwords and adds their two products to one FP32 partial sum. Both datapaths share the same accumulator addressing, active-lane mask, pipeline tags, forwarding path, and writeback control.

The active dimensions `tm` and `tn` may end within a spatial beat. The scheduler derives a CE × CE lane mask from the beat coordinates and suppresses lanes outside the active region. Suppressed lanes neither update the FPU pipeline state nor write the accumulator banks.

### 4.4.5 Spatial Scheduling

The MAC scheduler visits the active spatial beats of a tile in row-major beat order. With TE = 16 and CE = 8, a full tile is divided into four 8 × 8 regions. These regions form four independent accumulation chains through the four-stage FPU pipeline. After all four beats have issued, the result of the first beat has reached the forwarding point when the scheduler returns to that beat for the next reduction update.

Two consecutive MAC operations are dependent when they update the same tile and the same spatial beat. Their destination tiles are compatible when they identify the same tile. A dependent MAC waits until the preceding result reaches the forwarding point and then consumes that result as its addend. Consecutive updates to different beats of a compatible tile can occupy different FPU pipeline stages at the same time.

A boundary tile with a smaller `tm` or `tn` may have fewer active spatial beats. When the number of active beats is smaller than the FPU latency, the scheduler can return to a dependent beat before its preceding result reaches the forwarding point. The scheduler keeps the MAC active and issues that beat when the required result becomes available.

The scheduler preserves MAC program order. It holds one current operation and one look-ahead operation, allowing the next queued MAC to become active as the current instruction issues its final beat.

### 4.4.6 Pipeline Residency, Forwarding, and Drain

Pipeline residency is the period during which the newest results of a MAC remain in the FPU pipeline instead of being stored in the accumulator banks. Each pipeline stage carrying an unfinished MAC result also carries a tag with the logical tile identifier, TEW, spatial beat, active-lane mask, and writeback state. The resident tile is the tile identified by these tagged results. The term describes the tile currently retained in the FPU pipeline and does not restrict the number of tiles stored in the distributed accumulator array.

When a dependent MAC reaches the scheduler, the result for its compatible tile and matching spatial beat is forwarded directly from the final FPU pipeline stage as the next addend. The pipeline therefore preserves the newest value while the corresponding accumulator location can still contain an older value. The forwarded MAC result replaces that older accumulator value in the arithmetic dependency chain.

When a MAC targets a different tile, the destination is incompatible with the resident tile. The OPE marks the resident results for writeback, drains them into the accumulator banks, and then changes the resident tile. A mismatch between the next requested spatial beat and the result at the forwarding point also causes the older result to advance to accumulator writeback before the conflicting beat proceeds.

A tile subset move or a VLSU tile access is an external operation because it accesses a tile outside the FPU pipeline through either the VRF-facing move path or the VLSU Tile interface. Before an external operation reads or writes the resident tile, the OPE drains its newest MAC results into the accumulator banks. The external operation remains stalled until the drain finishes, so it observes or replaces the current tile value.

### 4.4.7 Tile Subset Moves

The tile-to-vector and vector-to-tile movers are fully pipelined at the VRF-word level. Once a move is active and the required VRF port is granted, the mover transfers one 256-bit VRF word per cycle. The last word of one move can retire while the next queued move is accepted, allowing back-to-back moves without an idle cycle between them.

A tile-to-vector move reads the selected tile rows or columns from the accumulator banks, selects the configured element slice from each 32-bit physical accumulator word, and packs the elements into consecutive 256-bit VRF words. Logical-zero metadata overrides stale physical data with zero before packing. A vector-to-tile move performs the reverse mapping. It captures an accepted VRF word until the accumulator write succeeds and updates only the selected bytes of each accumulator word. Row and column orientations use different bank and spatial-beat traversal patterns while sharing the same VRF datapath.

Zvt requires SEW to equal TEW for a Move Tile Subset instruction. The current hardware configuration uses 32-bit accumulator elements and TEW = 32 for tile moves. With TE = 16, one tile row contains 16 × 32 = 512 bits, so either move direction transfers that row as two 256-bit VRF words over two cycles. The accumulator datapath supports byte and half-word selection for TEW = 8 and TEW = 16 configurations, but those modes require a corresponding hardware TEW configuration.

### 4.4.8 Logical Tile Zero

`vtzero` establishes a logical zero value for the selected tile without immediately clearing its physical accumulator words. Before accepting `vtzero`, the OPE waits until no queued or executing MAC is using the tile. If the tile is resident in the FPU pipeline, the OPE drains its tagged results without writing them into the accumulator banks because the zero operation supersedes those results.

When `vtzero` is accepted, the OPE sets logical-zero metadata for the selected element slice in every spatial beat of the tile. A later MAC targeting a marked slice receives zero as its FPU addend. Tile-to-vector and VLSU reads also return zero for that slice even though the accumulator banks can still contain an older physical value.

A MAC writeback, vector-to-tile move, or VLSU tile write clears the logical-zero metadata for each byte slice it replaces. The newly written physical value is then visible to subsequent operations. `vtzero` does not issue the accumulator-wide physical flush signal.

### 4.4.9 Context Discard

`vtdiscard` invalidates the complete matrix accumulator context. The OPE accepts it only after MAC scheduling, tile moves, and Tile-interface accesses have become idle. If MAC results remain resident in the FPU pipeline, the OPE first drains and invalidates those results without writing them into the accumulator banks.

After the pipeline is empty and no accumulator access is active, `vtdiscard` asserts the accumulator flush signal. Every lane-local accumulator bank clears its physical storage on that clock edge, and the OPE clears all logical-zero metadata. Hardware reset performs the same physical clearing of the accumulator banks.

### 4.4.10 MAC Completion

A MAC produces its local completion event when its final required reduction and spatial beat is accepted by the FPU pipeline. The result of that beat may still be travelling through the pipeline when the instruction identifier is returned to the controller. Its pipeline tag continues to protect the destination tile after instruction completion.

A dependent MAC can consume a result belonging to a compatible resident tile through forwarding. An incompatible MAC causes the resident results to be written to the accumulator before changing the resident tile. An external operation also triggers writeback before accessing a resident tile. MAC completion marks the end of operand issue for that instruction and does not require its results to have reached the accumulator banks.

## 4.5 Vector Load Store Unit Tile Path

### 4.5.1 Request Buffering and Execution

The double-bandwidth VLSU executes conventional vector-memory operations and Load/Store Tile Subset Instructions. Incoming LSU requests enter a four-entry, non-fall-through FIFO in program order. A tile request remains at the queue head until its `matrix_enable` signal is asserted, its Tile Subset Specifier is valid, and the tile-transfer state machine is available.

When the tile-transfer state machine accepts a request, it records the tile identifier, row or column orientation, starting index, active element count, TEW, memory address, and instruction identifier. Conventional vector-memory requests continue through the VRF-facing datapath. A tile request uses the independent Tile interface between the VLSU and the OPE accumulator array.

The VLSU performs address generation and memory transfer for the request. The OPE decides when the requested accumulator tile can be accessed. A request that cannot yet access the Tile interface remains active in the VLSU and holds its request payload stable until the OPE asserts ready.

### 4.5.2 Tile Interface and Data Mapping

The Tile interface provides separate read and write channels between the VLSU and the distributed accumulator array. Load/Store Tile Subset Instructions therefore do not use the shared OPE/VAU VRF ports. The physical Tile word width is fixed when the hardware is generated:

```text
TileWordWidth = TE × AccumulatorElementWidth.
```

With TE = 16 and a 32-bit physical accumulator element, one Tile word is 512 bits. TEW selects the byte, half-word, or word slice that represents each architectural tile element within the 32-bit accumulator words.

A row-oriented transfer selects consecutive columns from one tile row. A column-oriented transfer selects one column across consecutive tile rows. For `vtse`, the OPE gathers the selected elements into a packed Tile word, and the VLSU writes that payload to memory. For `vtle`, the VLSU receives a packed payload from memory, and the OPE scatters its elements into the selected accumulator locations.

A `vtle` transfer updates only the byte slices selected by TEW. The OPE preserves the other slices in each physical accumulator word through a read-modify-write operation. Row and column transfers use different bank and spatial-beat traversal patterns but share the same Tile interface.

### 4.5.3 Logical-Zero Handling

The OPE applies logical-zero metadata when the VLSU reads a tile for `vtse`. The accumulator banks can still contain an older physical value after `vtzero`, so the OPE reads the physical word and replaces every marked byte slice with zero before constructing the Tile word. Unmarked slices retain their physical accumulator values. Memory therefore receives the architectural tile value even when only part of a 32-bit accumulator word is logically zero.

For each selected slice, the value returned through the Tile read channel is equivalent to:

```text
TileReadValue = LogicalZero ? 0 : PhysicalAccumulatorValue.
```

A `vtle` write replaces the selected physical accumulator slices and clears their logical-zero metadata. Subsequent MAC, move, and VLSU reads observe the newly loaded values. Logical-zero metadata for slices outside the `vtle` write remains unchanged.

### 4.5.4 TCDM Transfers

The VLSU divides a packed Tile word into ELEN-wide TCDM requests and distributes consecutive chunks across the available memory ports. In the current double-bandwidth configuration, eight 64-bit ports provide an aggregate peak transfer width of 512 bits per cycle. A complete 512-bit Tile word can be presented in one request wave when all eight accesses are accepted together.

The sustained transfer rate depends on the number of active elements, address alignment, TCDM bank availability, outstanding responses, and the gather or scatter pattern required by the selected orientation. Per-port tags distinguish tile traffic from conventional vector-memory traffic and record each response position within the packed Tile word.

For `vtle`, the VLSU collects the memory responses before presenting the completed Tile word to the OPE. The instruction completes after the OPE accepts the Tile write. For `vtse`, the VLSU first obtains the Tile word from the OPE, issues all required memory writes, and waits for their acknowledgements before reporting completion.

### 4.5.5 Coordination with Pipeline-Resident Results

A Load/Store Tile Subset Instruction is an external operation because it accesses a tile through the Tile interface rather than through the FPU pipeline. The accumulator banks must contain the newest tile value before `vtse` reads that tile. The OPE therefore detects a matching resident tile, writes its tagged MAC results into the accumulator banks, and withholds Tile-read ready until the drain finishes.

Before `vtle` writes a tile, the OPE checks for queued, executing, or pipeline-resident MAC updates to the same tile. A matching resident tile is drained before the Tile write is accepted. The controller's matrix scoreboard orders the `vtle` request against older matrix operations, while the OPE prevents a physical accumulator access from overlapping its local MAC or move activity.

The VLSU holds the Tile request stable during either wait. After the Tile-interface handshake and all required memory activity complete, the VLSU returns the request's instruction identifier to the controller. The controller then retires the corresponding matrix-scoreboard claim.
