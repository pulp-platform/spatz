# 5. System-Level and ISA Exploration

Chapter 4 described the implemented controller, OPE, and VLSU. This chapter examines what their parameters and the Zvt instruction model imply for a matrix workload before choosing a kernel schedule. It separates architectural instruction demand from physical OPE work, accumulator capacity, and movement across the TCDM, VRF, and Tile interface. Chapter 6 will address register allocation, output layout, and instruction scheduling.

## 5.1 Parameters and Scope

The application dimensions are `M`, `N`, and `K` for `C[M,N] += A[M,K] × B[K,N]`. The relevant architecture parameters are the vector length `VLEN`, the matrix tile edge `TE`, the physical OPE compute edge `CE`, source element width `SEW`, tile element width `TEW`, and the maximum reduction extent `KMAX`. The active reduction extent `tk` cannot exceed `KMAX`; the active output dimensions `tm` and `tn` cannot exceed the configured tile and vector-group limits.

The present Spatz configuration has VLEN = 512 bits, four FPUs, an eight-port double-bandwidth VLSU, and a 128 KiB TCDM divided into 16 banks. The OPE has CE = 8, TE = 16, and 32-bit physical accumulator elements. FP32-to-FP32 and widening FP16-to-FP32 are the arithmetic modes considered in this study. Other parameter values below are analytical design points; a result obtained for one of them is not a measurement of the present RTL. The [Spatz paper](https://arxiv.org/html/2309.10137#S3) motivates the compact 2 KiB VRF used at VLEN = 512, while [Zvt version 0.4](https://github.com/riscv/riscv-isa-manual/blob/zvt/src/unpriv/zvt.adoc) defines the tile and configuration constraints.

## 5.2 Vector Capacity and Matrix Configuration

Spatz has 32 architectural vector registers. At VLEN = 512, their total capacity is `32 × 512 / 8 = 2,048 bytes`. One register contains `EVE = VLEN / SEW` source elements: 16 FP32 elements or 32 FP16 elements. Zvt derives the matrix LMUL from the effective tile edge `ETE`, EVE, KMAX, and the widening factor TWIDEN. For the modes considered here, TEW = 32 and hence ETE = TE.

```text
LMUL = min(ceil(ETE / EVE), 8 / KMAX, 8 / TWIDEN)
```

For TE = 16, both FP32-to-FP32 (`EVE = 16`, `KMAX = 1`, `TWIDEN = 1`) and FP16-to-FP32 (`EVE = 32`, `KMAX = 2`, `TWIDEN = 2`) select LMUL = 1. At the analytical TE = 32 point, FP32 selects LMUL = 2 while widening FP16 still selects LMUL = 1. Thus a larger TE can reduce the number of matrix instructions while increasing the vector-register group required by an operand. The configuration instructions clamp `tm`, `tn`, and `tk` to the resulting limits. No kernel may assume that its requested dimensions were accepted without checking the values returned by those instructions.

VLEN is held at 512 throughout the evaluation. Sweeping it would change VRF capacity, vector instruction coverage, and possibly matrix LMUL at the same time. The comparisons in this chapter therefore isolate other parameters instead of attributing a change caused by several coupled resources to VLEN alone.

## 5.3 Architectural Instructions and Physical Compute Work

For a full tile, one Matrix Arithmetic Instruction covers a `TE × TE` output region and `tk` positions of the reduction dimension. If `M`, `N`, and `K` divide evenly by TE and `tk`, the instruction count and physical spatial-beat count are

```text
N_matrix = (M / TE) × (N / TE) × (K / tk)
N_beats  = N_matrix × (TE / CE)²
         = (M × N × K) / (CE² × tk)
```

For boundary tiles or a final short reduction group, `ceil(M / TE) × ceil(N / TE) × ceil(K / tk)` gives the number of matrix instructions when each tile and reduction group is configured separately. The actual work in the final tile or group is smaller than the full-tile upper bound; its active dimensions are set through `tm`, `tn`, and `tk`. The arithmetic problem still contains `M × N × K` scalar multiply-accumulate contributions regardless of the chosen instruction grouping.

For example, take `M = N = K = 64`, TE = 16, and CE = 8. FP32-to-FP32 uses `tk = 1`, giving 1,024 matrix instructions and 4,096 spatial beats. Widening FP16-to-FP32 can use `tk = 2`, giving 512 matrix instructions and 2,048 spatial beats. Both modes update the same number of output elements across the full reduction. The widening datapath performs two FP16 products per FP32 accumulation step, so beat counts alone do not express equivalent FPU operations or execution cycles.

At the analytical TE = 32, CE = 8 point, the same FP32 workload needs 256 matrix instructions with 16 spatial beats each, again totaling 4,096 beats. Changing TE changes how much work a single instruction describes; changing CE changes the number of physical regions through which that instruction is executed. The latter also changes compute-array size, so the beat count cannot by itself predict area, utilization, or runtime.

## 5.4 Accumulator and Transfer Scaling

At TEW = 32, Zvt provides four independently addressable tiles. Ignoring control metadata, their architectural storage scales as

```text
TileStateBytes = 4 × TE² × (TEW / 8)
```

The present TE = 16 configuration therefore provides `4 × 16² × 4 = 4 KiB` of tile storage. A TE = 32 design point would require 16 KiB for the same four TEW = 32 tiles. This fourfold growth follows from doubling both tile dimensions; it is not a measured area or energy estimate. Narrower TEW values reinterpret the tile storage as more logical tiles rather than increasing the total bytes.

The physical Tile interface width also depends on TE: `TileWordWidth = TE × 32 bits` in the present 32-bit accumulator organization. A TE = 16 row is 512 bits, matching the aggregate peak width of eight 64-bit TCDM ports. A TE = 32 row would be 1,024 bits and require at least two full-width memory request waves even under ideal acceptance. Alignment, TCDM bank conflicts, and response timing can add cycles. These widths concern the VLSU-to-tile path; a tile subset moved to the VRF uses 256-bit VRF words and a separate path.

Each input or output must be counted at the boundary it crosses. A conventional vector load moves an operand from TCDM to the VRF; a matrix instruction reads that operand from the VRF into the OPE. Reusing a loaded register avoids another TCDM load, although it does not eliminate each OPE operand access. A tile store moves a result from the OPE to TCDM without using the VRF. A tile-to-vector move followed by a vector store adds a Tile-to-VRF transfer and a VRF-to-TCDM transfer, but makes the result available to VAU post-processing. Element counts, transferred bytes, instruction counts, and transfer cycles are therefore distinct quantities.

## 5.5 System-Level Limits to Examine

Three possible limits follow from the architecture. First, Snitch must supply matrix configuration, vector loads, matrix arithmetic, address updates, and output instructions. A larger TE reduces arithmetic instruction demand for a fixed problem, but the front end still has to supply the other instructions. Second, the OPE needs operands from the shared VRF while the VAU may be preparing or processing vectors; contention can delay an otherwise ready operation. Third, tile stores and moves must observe completed tile values, so a result still resident in the FPU pipeline may have to reach the accumulator before the transfer proceeds.

The double-bandwidth VLSU raises the available peak TCDM request width, but sustained traffic also depends on banks, addresses, and concurrent requesters. Increasing TE raises tile capacity and Tile interface width as well as the work per matrix instruction. Changing precision alters input bytes, KMAX, and the available arithmetic datapath. These effects must be considered together when selecting an experiment. An instruction-count reduction alone does not establish a faster kernel.

## 5.6 Exploration Boundary

The supported reference point for the following chapters is VLEN = 512, CE = 8, TE = 16, with FP32-to-FP32 and widening FP16-to-FP32 arithmetic. TE = 32 and other parameter values provide analytical comparisons of instruction density, tile capacity, and transfer width. Measured latency, port contention, and utilization require an implemented configuration and an emitted instruction stream.

This chapter identifies the resources a kernel must manage. Chapter 6 will specify how operands, output tiles, vector registers, and stores are arranged over time. Later measurements can then compare a concrete instruction sequence with the work and traffic predicted here.
