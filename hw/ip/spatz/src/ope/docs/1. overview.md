# Spatz VME: Study Overview

## Research Focus

This study integrates the Zvt version 0.4 Vector Matrix Extension into the Snitch–Spatz system. Spatz already provides a compact vector register file (VRF), vector arithmetic, and access to a banked tightly coupled data memory (TCDM). The extension adds matrix configuration, an Outer Product Engine (OPE), and matrix tile state. Matrix instructions take their source operands from the VRF and accumulate into tiles, while existing vector instructions remain available for data preparation and result processing.

The central question is how to make matrix arithmetic useful in a complete GEMM kernel on a compact vector processor. Input loads, register allocation, instruction supply, tile transfers, and output processing can limit performance even when the arithmetic array is busy. The study considers FP32-to-FP32 and widening FP16-to-FP32 computation and examines how tile layout and instruction scheduling affect these costs.

## Design and Evaluation Questions

- **Operand and result movement:** How much data moves from TCDM to the VRF, from the VRF to the OPE, and from the tiles back to memory or vector registers? When does direct tile storage avoid a VRF transfer, and when is a tile-to-vector move useful for post-processing?
- **Shared resources:** How do the VAU and OPE share VRF access, and how do the controller and execution units preserve dependencies between vector and matrix instructions?
- **Tile geometry:** How do the architectural tile edge (TE), physical compute edge (CE), VRF word width, and Tile interface width affect instruction count, execution time, and transfer granularity?
- **Kernel mapping:** How do output tile layouts, vector register groups, FP16 operand packing, and store schedules affect input reuse, register lifetime, and overlap between computation and output transfer?
- **Measured behavior:** Which predicted costs appear in cycle-accurate simulations, and which stalls arise from instruction supply, memory accesses, VRF contention, or accumulator dependencies?

## Scope of the Work

The hardware contribution is the integration of the OPE and tile data paths into Spatz, including matrix configuration, instruction dispatch, dependency management, and coordination with the double-bandwidth VLSU. The software contribution is a set of matrix kernels and scheduling choices that exercise the FP32 and widening FP16 modes. An analytical model separates instruction counts, element transfers, and byte traffic before the measured performance is discussed.

TE describes the tile visible to a matrix instruction; CE describes the physical compute array that processes it. Changing CE can change the number and timing of physical execution beats without changing the number of architectural matrix instructions for a fixed TE and workload. Likewise, a tile-to-vector move uses the VRF path, while a tile load or store uses the VLSU Tile interface. The analysis treats these as distinct transfers.

## Chapter Roadmap

1. **Introduction** states the workload problem, research goals, and hardware and software contributions.
2. **[Background and Related Work](<2. Background and Related Work.md>)** introduces matrix dataflows, vector data movement, SSR, MX, O-POPE, and matrix engine integration choices. It compares where operands and partial sums reside and how results leave the compute unit.
3. **[System Overview and Spatz VME Architecture](<3. System Overview and Spatz VME Architecture.md>)** introduces Snitch, Spatz, the VRF, VAU, OPE, VLSU, and TCDM. It follows instruction dispatch and completion, then defines the software-visible Zvt configuration, tiles, arithmetic, and transfer operations.
4. **[Spatz VME Microarchitecture](<4. Spatz VME Microarchitecture.md>)** describes the implemented controller, scoreboards, shared VRF arbitration, distributed OPE, accumulator behavior, and VLSU Tile path.
5. **[System-Level and ISA Exploration](<5. System-Level and ISA Exploration.md>)** examines VLEN, TE, CE, precision, instruction demand, accumulator capacity, and the distinct VRF and Tile transfer paths. It separates analytical design points from the implemented configuration.
6. **[Kernel Design](<6. Kernel Design.md>)** will describe FP32 and packed FP16 operand layouts, output tile mappings, register allocation, configuration changes, and store schedules. This chapter is reserved for later writing.
7. **Experimental Methodology** specifies the hardware configuration, instruction cache and buffer, workloads, baselines, correctness checks, simulation procedure, and definitions of cycles and utilization.
8. **Results and Discussion** evaluates the kernel and hardware choices against the analytical predictions, using traces and measured cycles to explain bottlenecks and limitations.
9. **Conclusion and Future Work** summarizes the supported findings and identifies remaining architectural and software opportunities.

The analytical model establishes expected work and traffic; the experimental results determine whether a particular mapping or schedule improves execution on this implementation. Statements about issue limits and transfer cycles therefore refer to the specified register mapping and data path rather than to a general Zvt ISA limit.
