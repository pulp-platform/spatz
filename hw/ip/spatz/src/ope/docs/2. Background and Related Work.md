# 2. Background and Related Work

## 2.1 Matrix Workloads and Data Reuse

Matrix multiplication appears both as a standalone kernel and as one stage of a longer computation. Inputs may require packing, transposition, or conversion before multiplication. Outputs may be consumed by bias addition, scaling, activation, or quantization. The cost of these stages depends on where the operands and partial sums reside and how results reach the next operation. Arithmetic throughput alone therefore does not describe the cost of a complete matrix workload.

For a matrix product `C[M,N] += A[M,K] × B[K,N]`, an inner-product mapping computes each output element by reducing one row of `A` against one column of `B`. A row-wise vector mapping broadcasts an element of `A` across a row of `B` and updates a corresponding row of `C`; it offers contiguous vector accesses for row-major `B` and `C`, but keeping several output rows live consumes vector registers. An outer-product mapping uses a column segment of `A` and a row segment of `B` at each reduction step to update a two-dimensional region of `C`. Each input element is reused across one dimension of that region, while the output partial sums must remain available throughout the reduction.

Mixed-precision matrix multiplication reduces input storage and transfer width while retaining a wider accumulator. A widening FP16-to-FP32 operation, for example, consumes FP16 multiplicands and accumulates into FP32 results. The wider accumulator limits rounding during the `K` reduction, while input conversion and packing still contribute to the overall workload. These properties motivate examining memory traffic, register pressure, and output handling alongside the compute datapath.

## 2.2 Data Movement in Compact Vector Processors

A vector instruction applies one operation to multiple elements and amortizes instruction fetch and decode over the vector length. A vector register file (VRF) can also retain inputs and intermediate values close to the functional units, reducing accesses to shared L1 memory. In its floating-point Spatz cluster, Perotti et al. analyze this trade-off and use a compact, latch-based 2 KiB VRF per vector processing element. A small VRF lowers storage cost, but the available register capacity and ports constrain how many matrix operands and output partial sums can remain live at once. [Spatz paper](https://arxiv.org/html/2309.10137#S4)

Regular matrix loops also spend scalar instructions on address updates and explicit data transfers. Stream Semantic Registers (SSR) associate registers with configured memory streams, removing many explicit loads and stores from the inner loop of a scalar core. SSR primarily changes how operands are supplied; the storage of matrix partial sums depends on the compute architecture coupled to those streams. [SSR paper](https://arxiv.org/abs/1911.08356)

These approaches trade instruction traffic against data movement and local storage. A longer vector or a more aggressive loop unroll can reduce control overhead, but may occupy more registers or enlarge the instruction stream. A matrix instruction can describe more arithmetic work, yet still require packing, register transfers, and result writeback. The useful comparison is therefore the movement of `A`, `B`, and `C` through memory, the VRF, and the compute unit over the full kernel.

## 2.3 Matrix Engine Integration

Matrix extensions differ in how much of the vector datapath they reuse. MX extends Spatz by retaining the existing VRF and functional units, adding operand broadcast and a compact buffer near the FPUs to increase reuse during matrix multiplication. This limits new hardware but keeps matrix arithmetic tied to the throughput and scheduling of the vector functional unit. [MX paper](https://arxiv.org/abs/2401.04012)

Architectures with separate tile state keep output partial sums outside the ordinary vector registers. Arm SME, for example, provides ZA matrix storage with tile-slice transfers to vector registers and memory. Intel AMX provides tile registers and a tile-multiplication engine. These designs expose different tile organizations and transfer operations, so their peak arithmetic rates alone are not a sufficient basis for comparing full kernels. [Arm SME overview](https://learn.arm.com/insights/sme/) · [Intel AMX overview](https://www.intel.com/content/www/us/en/products/docs/accelerator-engines/what-is-intel-amx.html)

An outer-product engine can exploit the reuse of each operand across a two-dimensional compute array. O-POPE studies a pipelined implementation that uses FPU pipeline registers to hold intermediate results and reduce dedicated buffering. That work concerns the compute engine itself; integrating such an engine into a vector processor additionally requires instruction dispatch, register dependencies, memory access, and paths for moving tile results to later vector operations. [O-POPE paper](https://arxiv.org/abs/2606.02333)

## 2.4 Position of This Work

This work integrates a separate Outer Product Engine (OPE) into Spatz while retaining the VRF as the source of matrix operands. The OPE holds two-dimensional tile results, and the existing vector datapath remains available for input preparation and output processing. Tile transfers to and from memory provide another path for results that do not require a vector post-processing step. The design consequently combines a dedicated matrix compute and accumulator path with shared vector storage and a common instruction-control domain.

The questions addressed by this integration are concrete: how operands reach the OPE without adding dedicated VRF operand ports; how vector and matrix instructions remain ordered while using different result storage; and when tile results should pass through the VRF instead of moving directly to memory. Chapter 3 introduces the Snitch–Spatz system and the software-visible Zvt model. Chapter 4 describes the corresponding hardware paths and dependency mechanisms.
