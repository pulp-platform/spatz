# 3. System Overview and Spatz VME Architecture

This chapter introduces the Snitch–Spatz system, follows an instruction from the scalar core through Spatz, and describes the software-visible matrix state used by this work. The original Spatz instruction path and functional units are drawn from the [Spatz architecture paper](https://arxiv.org/html/2309.10137#S4). The matrix instruction semantics follow [Zvt version 0.4](https://github.com/riscv/riscv-isa-manual/blob/zvt/src/unpriv/zvt.adoc). Chapter 4 describes how the implementation realizes those semantics.

## 3.1 Snitch–Spatz Core Complex and Shared Memory

A Snitch scalar core and a Spatz vector processor form a core complex. Snitch executes scalar control instructions, including branches, loop-index updates, and address calculations. Spatz executes data-parallel instructions. They communicate through the CORE-V X-Interface (XIF): Snitch identifies an instruction for offload and supplies the instruction word and any scalar operands, while Spatz decodes and executes the vector operation. This division allows a small scalar core to control a wider datapath without implementing the vector functional units inside the scalar pipeline. [Spatz paper, Section IV-A](https://arxiv.org/html/2309.10137#S4.SS1)

Core complexes access a banked, tightly coupled data memory (TCDM) through the cluster interconnect. Conventional vector loads move data from TCDM into the VRF, and vector stores move it back. The cluster can also bring data from external memory into TCDM through its DMA path. The Zvt tile load and store instructions introduced in this work add a route between TCDM and matrix tile state, so their payload need not pass through the VRF.

The [default configuration for this study](../../../../../system/spatz_cluster/cfg/spatz_cluster.doublebw.dram.hjson) has a 128 KiB TCDM divided into 16 banks, VLEN = 512 bits, four vector FPUs, and eight 64-bit Spatz memory ports. The Spatz paper evaluates a two-core-complex cluster with the same total TCDM capacity and bank count, but its illustrated Spatz instance uses a number of memory ports that matches the number of functional units. The port count and bandwidth statements below refer to the present double-bandwidth configuration, not to the paper's baseline cluster.

## 3.2 Instruction Flow Across Snitch and Spatz

Snitch fetches an RVV or Zvt instruction in program order and performs the predecode needed to recognize an offloaded operation. It forwards the instruction and any required scalar register values over XIF. Snitch does not execute the vector or matrix datapath operation. Spatz's decoder interprets the instruction under the current vector and matrix configuration, identifies its execution class, and checks whether the request can be accepted.

The Spatz controller records the accepted instruction as an operation in progress, associates it with an instruction identifier, and sends the request to the appropriate unit. Matrix configuration instructions are handled in the controller. Ordinary vector arithmetic uses the Vector Arithmetic Unit (VAU), vector memory instructions use the Vector Load/Store Unit (VLSU), and permutation instructions use the Vector Slide Unit (VSLDU). Matrix arithmetic, tile subset moves, tile zero, and context discard use the OPE. Tile subset loads and stores use the VLSU and the OPE's Tile interface.

Acceptance of a request does not mean that it can begin using operands in the same cycle. The destination unit can buffer a request while an older instruction still owns a source register, destination register, tile, or memory resource. The controller's dependency state and the unit's local ready signals determine when the operation advances. Backpressure can therefore stop a request at dispatch, at an operand port, or at a destination unit without changing the program order observed by software.

As an operation runs, VRF access and memory responses may proceed over several cycles. A unit eventually returns a completion response with the same instruction identifier. The controller matches that response to the operation in progress, releases its dependency records, and reports completion through XIF when required. This flow applies to both RVV and Zvt operations, even though their results may reside in the VRF, a matrix tile, or TCDM. The precise queues, scoreboards, and completion timing are described in Chapter 4.

## 3.3 Controller, VRF, and Vector Execution

The controller maintains RVV configuration such as `vl` and `vtype`, including SEW and LMUL. These fields determine how many elements a vector instruction acts on and which physical registers form each vector register group. The controller also orchestrates the functional units and records register dependencies. In the original Spatz design, progress is tracked at the element level: a consumer can receive ready elements from an older vector producer before that producer has completed its entire vector instruction. Operand backpressure enforces hazards while allowing this vector chaining. [Spatz paper, Section IV-B](https://arxiv.org/html/2309.10137#S4.SS2)

The centralized VRF holds vector operands and intermediate values for the VAU, VLSU, and VSLDU. It also holds the matrix source operands used by the OPE and provides the endpoint for tile subset moves. The paper describes a small, latch-based VRF rather than a large private register file in each functional unit; the current VLEN = 512 configuration provides 32 architectural vector registers, or 2 KiB of vector state. Sharing this storage enables ordinary vector instructions to prepare matrix inputs and process tile outputs. The physical VRF port arbitration added for the OPE is described in Section 4.2. [Spatz paper, Section IV-C](https://arxiv.org/html/2309.10137#S4.SS3)

The VAU performs ordinary vector arithmetic using integer and floating-point units. The VSLDU performs vector slides and other element rearrangements. The VLSU executes conventional unit-stride, constant-stride, and indexed memory operations. When floating-point support is enabled, the FPU sequencer also manages scalar floating-point register access and scalar floating-point memory operations. These are parts of the Spatz baseline; the OPE adds matrix arithmetic and distributed tile storage alongside them. [Spatz paper, Sections IV-B–D](https://arxiv.org/html/2309.10137#S4.SS2)

## 3.4 Double-Bandwidth VLSU and Memory Paths

The Spatz paper describes a VLSU built from independent 64-bit memory interfaces. Independent ports can issue accesses to different TCDM banks for unit-stride, strided, and indexed patterns without forming one wide memory transaction. Since responses from different ports can arrive out of order, per-port response buffering and ordered VRF commit keep vector loads compatible with element-wise chaining. The narrow ports also use the same TCDM interconnect width as scalar accesses. [Spatz paper, Section IV-D.2](https://arxiv.org/html/2309.10137#S4.SS4.SSS2)

This study selects the double-bandwidth VLSU with eight 64-bit memory ports and two VRF-side VLSU interfaces. Its aggregate peak memory request width is 512 bits per cycle when all ports accept a request. The corresponding baseline with four ports offers 256 bits per cycle. These widths describe available ports, not guaranteed sustained bandwidth: TCDM bank conflicts, address alignment, response latency, competing requesters, and the access pattern can all reduce the achieved rate.

The double-bandwidth VLSU serves two data routes. Conventional vector loads and stores exchange data between TCDM and the VRF. `vtle` and `vtse` exchange data between TCDM and the OPE's tile state through a separate Tile interface. A tile store reads a row or column subset from the OPE before generating memory writes; a tile load collects memory data before presenting the subset to the OPE. The VLSU handles addresses, memory requests, and responses; the OPE owns the tile data. Section 4.5 describes the transfer granularity and synchronization with MAC results.

## 3.5 Zvt Matrix State and Configuration

[Zvt version 0.4](https://github.com/riscv/riscv-isa-manual/blob/zvt/src/unpriv/zvt.adoc) adds square matrix tiles as architectural state alongside the vector registers. Matrix arithmetic reads its multiplicands from vector register groups and updates a destination tile. SEW is the source element width; TWIDEN is the accumulator widening factor; and TEW = SEW × TWIDEN is the tile element width. The configured dimensions `tm`, `tn`, and `tk` select the active output rows, output columns, and reduction depth. `tn` is tied to the vector length `vl`.

The tile edge TE is an implementation parameter and a power of two. At TEW = 32, the architectural state comprises four TE × TE tiles, addressed as `mt0`, `mt4`, `mt8`, and `mt12`. Narrower TEW values reinterpret this same storage as more logical tiles. The current implementation uses TE = 16 and a 32-bit physical accumulator element. These numbers describe the current hardware configuration; Zvt software discovers usable dimensions through configuration instructions rather than assuming a fixed TE.

`msetmtype` establishes `mtype` and `vtype` from scalar registers. `msetmtypei` supplies SEW, TWIDEN, and `altfmt` as instruction fields and initializes the remaining matrix type fields to zero. Both forms set `vl` to zero and derive a matrix LMUL that respects the available vector elements per register, the tile edge, the widening factor, and KMAX. `msettn` then sets `tn` and `vl`; `msettm` and `msettk` set the other active dimensions. These instructions clamp requested sizes to the supported register and tile capacities. KMAX is one for SEW = 32 and two for SEW = 16 in the FP32 and widening FP16-to-FP32 modes considered here.

A vector configuration instruction such as `vsetvl` invalidates the current matrix type. It does not erase the stored tile contents. Software can therefore switch to a vector configuration for grouped loads or post-processing and later re-establish matrix configuration before another matrix operation. The architectural effect belongs to the Zvt model; the controller's CSR updates and dependency tracking are described in Section 4.3.

## 3.6 Zvt Operations and Visible Data Paths

Matrix Arithmetic Instructions update a tile from two vector source groups. In the FP32 mode, `vtfmm` adds an outer product with one reduction element per output element. In widening FP16-to-FP32 mode, the instruction can cover two reduction elements while accumulating in FP32. For a selected output region, the operation has the form

```text
C[i,j] += sum over k in the active tk range of A[k,i] × B[k,j].
```

Zvt also defines alternative-format floating-point and integer matrix arithmetic instructions. The kernels examined here focus on FP32-to-FP32 and FP16-to-FP32 `vtfmm`. A matrix operation uses tile state for the result, leaving its vector source groups available to be reused by other tile updates.

`vtzero` establishes a zero value for one tile before accumulation. `vtdiscard` discards the matrix context. These operations have different scopes: a subsequent operation can use a zeroed tile as an accumulator, while discard ends use of the previous tile values. Section 4.4 explains how the OPE represents logical zero and physically clears accumulator storage.

A Tile Subset Specifier (TSS) selects a tile, a row or column orientation, and an index. `vtmv.v.t` moves a selected tile subset into a vector register group; `vtmv.t.v` moves vector data into a tile subset. The move instructions require SEW = TEW. For an FP16-to-FP32 kernel, software therefore configures a 32-bit move after the matrix arithmetic phase before moving FP32 results into the VRF. `vtle` and `vtse` transfer selected tile rows or columns directly between memory and tile state, using the VLSU rather than the VRF.

## 3.7 End-to-End Matrix Data Flow

A tiled GEMM first establishes matrix configuration and places input operands in vector register groups through conventional vector loads. It initializes an output tile with `vtzero` or loads an existing addend with `vtle`. Successive `vtfmm` instructions read the vector operands and accumulate across `K` into that tile. The input vectors can be reused across multiple output tiles; the output partial sums remain in tile state instead of occupying VRF groups for the full reduction.

After the reduction, the output can follow either of two visible paths. `vtse` writes the tile subset directly to TCDM. If the next stage needs vector arithmetic, `vtmv.v.t` places the selected tile subset in the VRF, where the VAU can apply bias, scaling, activation, or another element-wise operation before an ordinary vector store. The latter path requires additional tile moves and may require vector and matrix configuration changes. The kernel mapping chapter examines how tile layout, register allocation, and instruction order affect these costs.
